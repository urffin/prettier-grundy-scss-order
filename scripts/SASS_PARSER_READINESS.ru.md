# Проверка готовности sass-parser [English](SASS_PARSER_READINESS.md)

Эта отдельно запускаемая проверка воспроизводит блокеры миграции, сохраняя производственный `postcss-scss`, сортировку и зависимости библиотеки. Шесть [минимальных fixtures](../tests/fixtures/sass-parser/README.md) охватывают процентные keyframes, комментарии между ветвями и в конце блока, игнорируемый текст, метаданные пробелов и обычный контрольный пример.

[Разбор upstream от 2026-11-18](../tests/fixtures/sass-parser/upstream/README.md) разделяет три проблемы разбора/печати и два требования адаптера. Добавлены независимый collector и неопубликованные черновики issues. Работа над Root raws не равна поддержке declaration `raws.before`; source spans сохраняют игнорируемый текст проверенного примера, но адаптер миграции не реализован и не одобрен. Существующая проверка готовности не меняется.

```sh
npm ci
npm run research:sass-parser -- --version 0.5.3 --output /external/directory/sass-parser-results.json
```

Укажите точную опубликованную версию, при необходимости prerelease. Теги, диапазоны, Git URL и пути вместо версии отклоняются. Команда устанавливает выбранный пакет из официального npm registry в отдельный временный проект ОС с отключёнными lifecycle-скриптами. Кандидат загружается и проверяется в свежем Node.js worker; после завершения удаляется только созданный временный проект. `package.json`, lockfile и `node_modules` репозитория не меняются. Для этого режима нужен доступ к registry.

Транзитивные зависимости могут изменяться между запусками даже при точной версии парсера. Поэтому JSON содержит фактические временные manifest и npm lockfile, SHA-256 от `JSON.stringify(packageLock)`, версии зависимостей кандидата и хеши entry/package. Чтобы повторить это дерево, сохраните `installation.packageJSON` и `installation.packageLock` как `package.json` и `package-lock.json` в другом изолированном каталоге, выполните там `npm ci --ignore-scripts`, затем используйте готовую установку:

```sh
npm run research:sass-parser -- --version 0.5.3 --package-root /isolated/node_modules/sass-parser --output /external/directory/recheck.json
```

`--package-root` не требует установки или сети. Worker всё равно сверяет имя пакета и точную запрошенную версию; переданный каталог не изменяется и не удаляется. Отчёт содержит `installation.kind: "existing-package"`, версии/хеши, но не утверждает создание нового lockfile. В PowerShell используйте `npm.cmd`, если обёртка поглощает разделитель `--`.

## Отчёт и коды завершения

Schema version 1 содержит окружение и идентификатор worker, точные версии кандидата и эталонов, хеши fixtures/входов, исходный/первый/второй текст, статусы проверок `pass` / `fail` / `skipped`, структурированные ошибки парсера и итоговые счётчики. Сначала входы компилируются Dart Sass из зависимостей репозитория, чтобы не принять ошибочный fixture за проблему кандидата. Компиляция вывода кандидата как доказательство семантической эквивалентности не выполняется.

- `completed: true` означает, что исследование выполнено; `status: "blocked"` — корректный измеренный результат.
- `minimumChecksPassed` и `readyForCorpus` становятся true только после успеха всех проверок всех минимальных примеров. Пропущенная проверка не считается успешной.
- `migrationApproved` всегда false. Успех разрешает лишь следующее исследование: полный закреплённый корпус, затем адаптер, браузерная интеграция и производительность.
- Ошибки установки/импорта/API/fixtures дают `completed: false`, `status: "error"`, `error.phase` и не превращаются в положительный результат готовности.

По умолчанию код **0** означает выполненное исследование, включая обнаруженные блокеры; **1** — ошибку инфраструктуры или CLI. С `--require-pass` обнаруженные блокеры дают код **2**, например для явно включаемого readiness gate:

```sh
npm run research:sass-parser -- --version 0.5.3 --require-pass --output /external/directory/gate.json
```

Кандидат не добавляется в штатную матрицу совместимости. `npm test` проверяет fixtures, оценку результатов и CLI без сети, используя синтетический пакет в свежем worker. Команда не запускает полный корпус автоматически, не добавляет production-адаптер и не одобряет миграцию. Скорость, память и браузерная поддержка не измеряются. Статус разработки самого парсера описан в [официальном README](https://github.com/sass/dart-sass/tree/main/pkg/sass-parser#readme); пригодность для этого форматтера устанавливается сохранёнными проверками.

## GitHub Actions: вручную и раз в неделю

Отдельный [workflow Sass parser readiness](../.github/workflows/sass-parser-readiness.yml) принимает точную версию для ручного запуска. Еженедельный запуск — по понедельникам в **06:23 UTC / 09:23 МСК**, на default-ветке. По расписанию запрашивается официальный npm endpoint `latest`, проверяются и сохраняются точная stable-версия и integrity, затем эта зафиксированная версия передаётся в probe. Prerelease можно выбрать вручную. Еженедельная проверка выполняется и без смены версии парсера: дерево его зависимостей могло обновиться.

Workflow использует Node.js 24 и права только на чтение репозитория. Результат независим от обычной push/PR-матрицы:

- `passed`: минимальные fixtures прошли; исследование полного корпуса ещё необходимо.
- `blocked`: исследование выполнено, блокеры воспроизведены. Задание успешно, список блокеров виден в summary.
- `error`: сбой выбора версии, подготовки, установки, импорта, API или проверки отчёта. Шаг probe завершается с ошибкой, задание красное.

До `npm ci` создаётся JSON-заготовка ошибки, требующая только встроенных модулей Node. Summary и загрузка артефакта с `always()` сохраняют evidence при сбоях зависимостей/probe. Сбой до checkout или настройки Node не позволяет создать заготовку. Артефакт **`sass-parser-readiness-results`** хранится 30 дней: schema-1 envelope с `kind: "sass-parser-readiness-ci"`, статусом, GitHub run/commit context, выбором версии и полным исследовательским отчётом; исходный `*.probe.json` также включён, когда probe запускался. Integrity из scheduled selection сверяется с установленным lockfile. Обёртка отклоняет противоречивые счётчики/флаги/входы и пропущенные проверки. Файлы исключены из npm-пакета.

`npm run research:sass-parser:ci` — обёртка workflow. Она читает `SASS_PARSER_VERSION` для `workflow_dispatch`; `schedule` разрешает npm `latest`. Внутренние режимы `--initialize` и `--summarize` работают без установленных зависимостей. `SASS_PARSER_REPORT` задаёт путь JSON, иначе используется `RUNNER_TEMP` (локально — текущий каталог). Код 0 означает `passed` или `blocked`; ошибки выполнения дают 1. Код 2 с `--require-pass` у самостоятельной исследовательской команды сохраняется.

Событие GitHub [`release`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#release) относится к релизам этого репозитория и не подписывается на публикации чужого npm-пакета. Для немедленного запуска после upstream-публикации нужен внешний обработчик, вызывающий `repository_dispatch` или `workflow_dispatch`; такого обработчика здесь нет. Автоматизация выполняется еженедельным опросом. Запуски [по расписанию](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) могут задерживаться; в публичном репозитории расписание может отключиться после 60 дней без активности. Workflow станет доступен после попадания файла в default-ветку. Он не меняет production-парсер и не публикует релизы.
