# Разработка и benchmark [English](DEVELOPMENT.md)

Команды ниже выполняются из корня клонированного репозитория, а не из проекта с установленным npm-пакетом. [Документация плагина](../ru/README.md).

## Поддерживаемая матрица

Матрица CI охватывает актуальные patch-версии Node.js 22, 24 и 26 с Prettier 3.8.1 (минимальная поддерживаемая версия) и последней стабильной 3.x. Все шесть сочетаний проверяются на Linux; Node.js 24 с последней Prettier 3.x также проверяется на Windows. Подвижный селектор `3` остаётся внутри диапазона peer dependency и не подключает Prettier 4 или предварительные версии.

При push и pull request запускаются тесты, `npm run test:types` и `npm run test:package`. Последняя команда устанавливает настоящий tarball в отдельный временный проект и проверяет публичные экспорты, все пресеты, оба режима, конфигурацию, комментарии, идемпотентность и типы установленного пакета. Публикация релиза ожидает тот же общий набор проверок.

Для локальной проверки: `npm ci`, `npm test`, `npm run test:types`, `npm run test:package`. Проверке пакета нужен доступ к реестру. Sass и TypeScript используются только как dev-зависимости проверок и не добавляются в runtime-зависимости опубликованной библиотеки.

Матрица Node.js 24/Linux также запускает [standalone browser smoke](BROWSER.ru.md) с минимальной/последней Prettier 3.x: сравнивает оба режима и все пресеты с Node.js и сохраняет отдельные JSON-артефакты. esbuild и Playwright используются только как devDependencies.

Четыре дополнительных задания runtime-зависимостей покрывают все сочетания minimum/latest для PostCSS и postcss-scss с закреплённой Prettier. Каждое устанавливает свежий tarball плагина, проверяет фактическое дерево зависимостей и выполняет тот же Node/browser smoke: оба режима, комментарии, direct/fallback и карты. В артефактах записываются точные версии, профиль и lockfile установки. См. [селекторы и JSON evidence](BROWSER.ru.md#матрица-runtime-зависимостей).

## Benchmark

`npm run benchmark` охватывает семь синтетических сценариев (независимые/конфликтующие декларации, вложенные блоки, комментарии, if/else) и пять пакетов реальных файлов: `real-grundyjs`, `real-grundyjs-6f9645c`, `real-landos`, `real-falcon`, `real-eywa`. Зафиксированный корпус содержит 212 целых файлов, включая обновлённый снимок сайта (60 файлов: 58 CSS/два SCSS) и сохранённый архив (53 файла: 51 CSS/два SCSS). Каждый файл обрабатывается отдельно; замер охватывает весь пакет проекта. По умолчанию проверяются `strict` и `loose`. `sort` измеряет создание сортировщика и упорядочивание готовых AST без разбора и сериализации; `format` — полный вызов `prettier.format`. Результаты всех файлов удерживаются до последнего снимка памяти.

По умолчанию `--metric all` измеряет время и память в отдельных последовательных процессах. Для времени: два процесса на сочетание версии/режима/измерения, три прогрева и девять образцов каждого сценария в процессе. Принудительного GC в замерах времени нет. Один worker не загружает две версии кода. При сравнении порядок версий чередуется между раундами процессов. Отчёт содержит медианы, квартили, исходные выборки, PID и время начала процесса (`timeOriginMs` различает повторно использованные PID), версии runtime/пакета, Git-ревизии и хеши вывода. Замеры характеризуют конкретную машину и нагрузку; небольшая разница не гарантирует общего ускорения или уменьшения памяти.

Для памяти: три свежих процесса на **версию/режим/измерение/сценарий**, по одной операции без прогрева в каждом. Worker запускается с `--expose-gc`: два вызова GC перед исходным снимком и два после операции. Результат AST/строка удерживается до последнего снимка; хеширование и сериализация AST выполняются затем. Для `sort` AST подготовлен до исходного снимка; `format` охватывает весь вызов форматирования. Отдельный процесс для каждого сценария исключает влияние предыдущих сценариев на `maxRSS`.

```sh
npm run benchmark -- --output benchmark-results.json
npm run benchmark -- --compare v0.4.7 --output benchmark-results.json
npm run benchmark -- --scenario comments --safety strict --measurement format
npm run benchmark -- --scenario real-grundyjs --output benchmark-results.json
npm run benchmark -- --metric memory --compare v0.4.7 --memory-processes 3 --output benchmark-results.json
npm run benchmark -- --metric time --scenario independent-1000
npm run benchmark -- --help
```

В Windows PowerShell используйте `npm.cmd run benchmark -- ...`, если обёртка `npm.ps1` поглощает разделитель `--`. Можно вызвать скрипт напрямую: например, `node scripts/benchmark.mjs --scenario comments` (без разделителя).

`--compare` принимает локально доступный Git-коммит или тег (при необходимости сначала получите его через fetch). Исходники runtime копируются во временный каталог, обе версии используют установленные зависимости текущего checkout и тот же Node.js. Сравнивается код, а не исторические деревья зависимостей; старые install-скрипты не запускаются, рабочее дерево не меняется. Нужна поддержка режимов безопасности (0.3.0 или новее). Отличия вывода отмечаются как `outputMatches: false` и не прерывают замеры. Отрицательный `changePercent` означает, что текущий checkout быстрее. `--warmup`, `--samples` и `--processes` управляют замерами времени, `--memory-processes` — независимыми образцами памяти. Короткие прогоны подходят для проверки инструмента, а не выводов о скорости.

JSON **schema version 2** сохраняет время в `rows`/`workers` и добавляет `memoryRows`/`memoryWorkers` (у невыбранной метрики массивы пусты). Строки памяти содержат `before`, `after`, `afterGC`, `deltaAfter` и `deltaAfterGC` с `medianBytes`, квартилями и `samplesBytes` каждого поля; исходные снимки остаются в workers. Дельты считаются внутри каждого процесса до агрегации и могут быть отрицательными. При сравнении версий добавляется `changeBytes` (медиана current минус baseline) для heap после операции, heap после GC и maxRSS. Хеши входа/вывода времени и памяти одной версии должны совпасть; различия между версиями остаются информационными.

Поля памяти: `rss`, `heapTotal`, `heapUsed`, `external`, `arrayBuffers`, `maxRSS`, все в **байтах**. `arrayBuffers` уже входит в `external`, складывать их нельзя. Node возвращает `maxRSS` в KiB; в JSON он переведён в байты и отражает максимум процесса до последнего снимка, включая запуск, импорты, подготовку входа и GC. Снимки не измеряют все аллокации или точный пик heap; maxRSS охватывает весь процесс. Подробнее: [память Node.js](https://nodejs.org/docs/latest-v22.x/api/process.html#processmemoryusage) и [resource usage](https://nodejs.org/docs/latest-v22.x/api/process.html#processresourceusage).

JSON `inputs` содержит тип сценария, число файлов, объём и хеш входа. Для реальных пакетов также записаны исходный коммит, digest корпуса и хеши отдельных файлов; хеширование учитывает границы файлов. Сравнивайте производительность на одинаковых входах. По умолчанию 12 сценариев дают 48 строк времени и 48 строк памяти на сравнение, со статистикой каждой выбранной версии.

CI сравнивает текущую ревизию с закреплённым коммитом `dad2aa8dd42553c15dd7c021043a04d214f1ad37` на одном раннере с одинаковыми зависимостями. Версии запускаются последовательно в отдельных процессах; во втором раунде их порядок меняется на обратный. Измеряются оба режима, сортировка/полное форматирование и время/память. CI записывает сравнительные таблицы (память показана в MiB) и сохраняет общий `benchmark-results.json` на 14 дней. Каждая строка содержит статистику `current`/`baseline`, совпадение вывода и разницу в процентах/байтах. Порогов нет; ошибки выполнения по-прежнему приводят к провалу задания. Отчёт, корпус и скрипты benchmark исключены из npm-пакета.

В `npm test` включены 18 регрессионных SCSS-fixtures для всех пресетов и режимов. `npm run test:corpus -- --output corpus-results.json` проверяет хеши снимков, идемпотентность, комментарии, состав AST и побайтное совпадение вывода с эталонным путём через Processor для всех реальных файлов (4240 случаев, включая сохранённый архив); CI сохраняет отдельный отчёт. Прикладные файлы не компилируются по отдельности, общая эквивалентность CSS не утверждается. Обновление растущих стилей сайта явно: `npm run corpus:update -- --project grundyjs.ru --root /path/to/grundyjs.ru --check`, затем без `--check` для импорта закоммиченных стилей. Изменения рабочего дерева в снимок не попадают. Подробнее: [происхождение корпуса, гарантии регрессий и обновление](../tests/fixtures/corpus/README.md).

Для замеров этапов, счётчиков пар/рёбер и CPU-профилей на закреплённом корпусе: `npm run profile:real -- --output /external/directory`. См. [методику и результаты профилирования](./PROFILE_REAL.md); измерители добавляются только во временные снимки исходников. Реализация находится в `scripts/profile/`; прежние CLI и пути импорта, форматы отчётов сохранены, а хеши инструментов учитывают точки входа и реализацию.

Для сравнения Prettier без плагина, публичных `loose`/`strict` и эталона Processor на исходных и уже отформатированных файлах корпуса: `npm run research:format-pipeline -- --output /external/directory`. [Руководство по сравнению pipeline](./RESEARCH_FORMAT_PIPELINE.md) описывает прогретое время, отдельные замеры памяти первого вызова и прогретого процесса, а также фиксированный checkout для исторических экспериментов с преобразованиями и фазами. Эти прототипы больше не поддерживаются на текущем runtime.

Плагин Prettier напрямую вызывает разбор SCSS, сортировку и сериализацию, затем использует парсер и принтер Prettier. Для разобранных карт исходников и корневых аннотаций `sourceMappingURL` сохраняется Processor. Этот внутренний путь действует в обоих режимах сортировки без новой настройки. Точка подключения PostCSS-плагина прежняя.

## Готовность официального Sass-парсера

`npm run research:sass-parser -- --version 0.5.3 --output /external/directory/sass-parser-results.json` воспроизводит минимальные блокеры миграции с изолированной точной версией кандидата. См. [методику, JSON и коды завершения](SASS_PARSER_READINESS.ru.md). Выполненное исследование может обнаружить блокеры; успех минимальных примеров не одобряет production-миграцию.

Отдельный Actions workflow Sass parser readiness поддерживает точную версию вручную и еженедельную проверку npm latest по понедельникам. JSON сохраняется и при сбоях подготовки/probe; успешное исследование с `blocked` отделено от красной ошибки запуска. На push/PR этот workflow не запускается.
