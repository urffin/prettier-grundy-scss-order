# prettier-grundy-scss-order [English](../README.md)

[![npm][npm-badge]][npm] [![GitHub Actions Workflow Status][npm-build]][github-actions]

Поддерживайте порядок в SCSS, даже когда проект растёт. `prettier-grundy-scss-order` — плагин для [Prettier](https://prettier.io/), который при каждом форматировании размещает свойства, переменные, директивы Sass и вложенные правила в предсказуемом порядке.

Он создан для реальных SCSS-проектов: единообразно располагайте свойства раскладки, отделяйте логические блоки пустыми строками и переходите со знакомых правил сортировки, сохраняя присваивания переменных и вызовы миксинов на месте.

## Зачем это нужно?

- **Одна команда форматирования — один стиль для всей команды.** Больше никаких замечаний в ревью о порядке свойств.
- **Сортировка с пониманием SCSS.** Группируйте CSS-переменные, декларации, директивы Sass и вложенные правила, учитывая присваивания переменных и вызовы миксинов как границы сортировки.
- **Используйте привычный стандарт.** Выберите `csscomb`, `csscomb-yandex`, `csscomb-zen` или `pepelsbey`.
- **Задайте свой порядок.** Создавайте группы по типу узла, префиксу свойства или явному списку свойств.

## До и после

```scss
.card {
    padding: 16px;
    color: white;
    --card-color: #222;
    display: flex;
}
```

```scss
.card {
    --card-color: #222;
    color: white;
    display: flex;
    padding: 16px;
}
```

## Быстрый старт

Установите Prettier и плагин:

```bash
npm install --save-dev prettier prettier-grundy-scss-order
```

Добавьте плагин в `prettier.config.mjs`:

```js
export default {
    plugins: ["prettier-grundy-scss-order"]
};
```

Затем форматируйте SCSS обычным способом:

```bash
npx prettier --write "src/**/*.scss"
```

Порядок по умолчанию:

```text
@use → @extend → CSS-переменные → Sass-переменные → @if → декларации → @include → @mixin → вложенные правила
```

Декларации в группе `decl` сортируются по алфавиту. По умолчанию конфликты свойств и границы выполнения ограничивают перестановки на корневом уровне и внутри вложенных правил. Явно выберите режим `loose`, чтобы применять заданный порядок через эти границы.

## Настройка

Задайте опции в конфигурации Prettier:

```js
export default {
    plugins: ["prettier-grundy-scss-order"],
    grundyScssSorterSplitGroup: true,
    grundyScssSorterGroupsOrder: ["--variable", "$variable", "layout", "typography", "decl", "@include", "rule"],
    grundyScssSorterGroups: JSON.stringify({
        layout: {
            oneOf: ["display", "position", "inset", "width", "height", "margin", "padding"],
            order: "exact"
        },
        typography: {
            startsWith: "font",
            type: "decl"
        }
    })
};
```

| Опция | Описание | По умолчанию |
| --- | --- | --- |
| `grundyScssSorterGroupsOrder` | Имена групп в нужном порядке. Узлы, не соответствующие перечисленным группам, размещаются после них. | `[@use, @extend, --variable, $variable, @if, decl, @include, @mixin, rule]` |
| `grundyScssSorterWithRoot` | Сортировать узлы корневого уровня, а также декларации внутри правил. | `true` |
| `grundyScssSorterSplitGroup` | Добавлять пустую строку между группами. Группы с пометкой разделения также разделяют свои элементы. | `false` |
| `grundyScssSorterGroups` | JSON-строка с пользовательскими группами. Они дополняют встроенные группы. | — |
| `grundyScssSorterPreset` | Встроенный пресет порядка свойств. | — |

## Совместимость и проверки

### Обновление до 0.4.0

Некорректная конфигурация теперь вызывает ошибки: проверьте имена пресетов и групп, JSON групп, типы узлов и критерии; для `order: "exact"` укажите `oneOf`. Приоритет: явное значение → пресет → default. С пресетами `csscomb`, `csscomb-yandex`, `csscomb-zen` и `pepelsbey` неуказанный `grundyScssSorterWithRoot` теперь наследует `false`; для сохранения прежней сортировки корня явно задайте `true`. Без пресета значение остаётся `true`. Явный `grundyScssSorterSplitGroups: false` перекрывает `true` из `pepelsbey`. Режим безопасности по умолчанию остаётся `strict`, а `loose` включается явно. Подробности — в [истории изменений](../CHANGELOG.md).

### Поддерживаемая матрица

Матрица CI охватывает актуальные patch-версии Node.js 22, 24 и 26 с Prettier 3.8.1 (минимальная поддерживаемая версия) и последней стабильной 3.x. Все шесть сочетаний проверяются на Linux; Node.js 24 с последней Prettier 3.x также проверяется на Windows. Подвижный селектор `3` остаётся внутри диапазона peer dependency и не подключает Prettier 4 или предварительные версии.

При push и pull request запускаются тесты, `npm run test:types` и `npm run test:package`. Последняя команда устанавливает настоящий tarball в отдельный временный проект и проверяет публичные экспорты, все пресеты, оба режима, конфигурацию, комментарии, идемпотентность и типы установленного пакета. Публикация релиза ожидает тот же общий набор проверок.

Для локальной проверки: `npm ci`, `npm test`, `npm run test:types`, `npm run test:package`. Проверке пакета нужен доступ к реестру. Sass и TypeScript используются только как dev-зависимости проверок и не добавляются в runtime-зависимости опубликованной библиотеки.

### Benchmark

`npm run benchmark` охватывает семь синтетических сценариев (независимые/конфликтующие декларации, вложенные блоки, комментарии, if/else) и четыре пакета реальных файлов: `real-grundyjs`, `real-landos`, `real-falcon`, `real-eywa`. Зафиксированный корпус содержит 152 целых файла, включая 51 CSS и два SCSS из развивающихся стилей grundyjs.ru. Каждый файл обрабатывается отдельно; замер охватывает весь пакет проекта. По умолчанию проверяются `strict` и `loose`. `sort` измеряет создание сортировщика и упорядочивание готовых AST без разбора и сериализации; `format` — полный вызов `prettier.format`. Результаты всех файлов удерживаются до последнего снимка памяти.

По умолчанию `--metric all` измеряет время и память в отдельных последовательных процессах. Для времени: два процесса на сочетание версии/режима/измерения, три прогрева и девять образцов каждого сценария в процессе. Принудительного GC в замерах времени нет. Один worker не загружает две версии кода. При сравнении порядок версий чередуется между раундами процессов. Отчёт содержит медианы, квартили, исходные выборки, PID и время начала процесса (`timeOriginMs` различает повторно использованные PID), версии runtime/пакета, Git-ревизии и хеши вывода. Замеры характеризуют конкретную машину и нагрузку; небольшая разница не гарантирует общего ускорения или уменьшения памяти.

Для памяти: три свежих процесса на **версию/режим/измерение/сценарий**, по одной операции без прогрева в каждом. Worker запускается с `--expose-gc`: два вызова GC перед исходным снимком и два после операции. Результат AST/строка удерживается до последнего снимка; хеширование и сериализация AST выполняются затем. Для `sort` AST подготовлен до исходного снимка; `format` охватывает весь вызов форматирования. Отдельный процесс для каждого сценария исключает влияние предыдущих сценариев на `maxRSS`.

```sh
npm run benchmark -- --output benchmark-results.json
npm run benchmark -- --compare v0.4.3 --output benchmark-results.json
npm run benchmark -- --scenario comments --safety strict --measurement format
npm run benchmark -- --scenario real-grundyjs --output benchmark-results.json
npm run benchmark -- --metric memory --compare v0.4.5 --memory-processes 3 --output benchmark-results.json
npm run benchmark -- --metric time --scenario independent-1000
npm run benchmark -- --help
```

В Windows PowerShell используйте `npm.cmd run benchmark -- ...`, если обёртка `npm.ps1` поглощает разделитель `--`. Можно вызвать скрипт напрямую: например, `node scripts/benchmark.mjs --scenario comments` (без разделителя).

`--compare` принимает локально доступный Git-коммит или тег (при необходимости сначала получите его через fetch). Исходники runtime копируются во временный каталог, обе версии используют установленные зависимости текущего checkout и тот же Node.js. Сравнивается код, а не исторические деревья зависимостей; старые install-скрипты не запускаются, рабочее дерево не меняется. Нужна поддержка режимов безопасности (0.3.0 или новее). Отличия вывода отмечаются как `outputMatches: false` и не прерывают замеры. Отрицательный `changePercent` означает, что текущий checkout быстрее. `--warmup`, `--samples` и `--processes` управляют замерами времени, `--memory-processes` — независимыми образцами памяти. Короткие прогоны подходят для проверки инструмента, а не выводов о скорости.

JSON **schema version 2** сохраняет время в `rows`/`workers` и добавляет `memoryRows`/`memoryWorkers` (у невыбранной метрики массивы пусты). Строки памяти содержат `before`, `after`, `afterGC`, `deltaAfter` и `deltaAfterGC` с `medianBytes`, квартилями и `samplesBytes` каждого поля; исходные снимки остаются в workers. Дельты считаются внутри каждого процесса до агрегации и могут быть отрицательными. При сравнении версий добавляется `changeBytes` (медиана current минус baseline) для heap после операции, heap после GC и maxRSS. Хеши входа/вывода времени и памяти одной версии должны совпасть; различия между версиями остаются информационными.

Поля памяти: `rss`, `heapTotal`, `heapUsed`, `external`, `arrayBuffers`, `maxRSS`, все в **байтах**. `arrayBuffers` уже входит в `external`, складывать их нельзя. Node возвращает `maxRSS` в KiB; в JSON он переведён в байты и отражает максимум процесса до последнего снимка, включая запуск, импорты, подготовку входа и GC. Снимки не измеряют все аллокации или точный пик heap; maxRSS охватывает весь процесс. Подробнее: [память Node.js](https://nodejs.org/docs/latest-v22.x/api/process.html#processmemoryusage) и [resource usage](https://nodejs.org/docs/latest-v22.x/api/process.html#processresourceusage).

JSON `inputs` содержит тип сценария, число файлов, объём и хеш входа. Для реальных пакетов также записаны исходный коммит, digest корпуса и хеши отдельных файлов; хеширование учитывает границы файлов. Сравнивайте производительность на одинаковых входах. По умолчанию 11 сценариев дают 44 строки времени и 44 строки памяти с отдельной статистикой выбранных версий.

CI запускает обе метрики текущей версии, записывает таблицы времени и памяти (память показана в MiB) и сохраняет общий `benchmark-results.json` как артефакт на 14 дней. Порогов нет; ошибки выполнения по-прежнему приводят к провалу задания. Отчёт, корпус и скрипты benchmark исключены из npm-пакета.

В `npm test` включены 15 регрессионных SCSS-fixtures для всех пресетов и режимов. `npm run test:corpus -- --output corpus-results.json` проверяет хеши снимков, идемпотентность, комментарии и состав AST всех реальных файлов (3040 случаев); CI сохраняет отдельный отчёт. Прикладные файлы не компилируются по отдельности, общая эквивалентность CSS не утверждается. Обновление растущих стилей сайта явно: `npm run corpus:update -- --project grundyjs.ru --root /path/to/grundyjs.ru --check`, затем без `--check` для импорта закоммиченных стилей. Изменения рабочего дерева в снимок не попадают. Подробнее: [происхождение корпуса, гарантии регрессий и обновление](../tests/fixtures/corpus/README.md).

## Приоритет и проверка настроек

Приоритет: явное значение → выбранный пресет → пресет по умолчанию. Явное `false` перекрывает `true`. Без пресета сортировка корня включена, разделение групп выключено. Все четыре дополнительных пресета отключают сортировку корня, а `pepelsbey` включает разделение групп. Чтобы сортировать корень с этими пресетами, укажите `grundyScssSorterWithRoot: true` явно.

Определения групп объединяются по имени: defaults → пресет → пользовательские группы. Новое определение целиком заменяет группу, а не дополняет отдельные критерии. Непустой `grundyScssSorterGroupsOrder` заменяет порядок пресета; отсутствующий или пустой массив наследует его. Повторения имён групп и элементов `oneOf` допустимы; приоритет задаёт первое вхождение.

Невалидный JSON, группа не в виде объекта, неизвестные критерии и типы узлов, неверные типы значений, неизвестный пресет и ссылка на неопределённую группу вызывают ошибку с именем настройки или группы. Для `order: "exact"` обязателен массив `oneOf`. Пустые списки допустимы и ничего не выбирают; группа `{}` подходит ко всем сортируемым конструкциям. Критерии внутри группы соединяются через AND. Определённая группа, не совпавшая ни с одной конструкцией, допустима.

Конструкции, не попавшие в перечисленные группы, сохраняют взаимный порядок после них с учётом режима безопасности. Неизвестные at-rules имеют `type: "atrule"`. Комментарии остаются прикреплёнными к конструкциям и отдельно не сортируются.

Два изменения прежнего поведения: опечатки в конфигурации теперь вызывают ошибку, а неуказанная сортировка корня наследует пресет. Возможность явно выбрать режим `loose` сохраняется.

## Встроенные группы

| Группа | Что включает |
| --- | --- |
| `@use` | Инструкции Sass `@use` |
| `@extend` | Инструкции Sass `@extend` |
| `--variable` | Пользовательские CSS-свойства |
| `$variable` | Переменные Sass |
| `@if` | Инструкции Sass `@if`; связанные блоки `@else` остаются вместе с ними |
| `decl` | CSS-декларации, по умолчанию сортируются по алфавиту |
| `@include` | Инструкции Sass `@include` |
| `@mixin` | Объявления Sass `@mixin` |
| `rule` | Вложенные селекторы и правила |
| `@media`, `@supports` | Медиа- и feature-query-правила; добавьте их в порядок, когда это необходимо |

## Пользовательские группы

В каждой группе можно сочетать следующие критерии:

| Критерий | Значение | Пример |
| --- | --- | --- |
| `type` | Соответствует типу узла SCSS. | `{ type: "decl" }` |
| `startsWith` | Соответствует имени узла, начинающемуся с указанной строки. | `{ startsWith: "font", type: "decl" }` |
| `oneOf` | Соответствует одному из перечисленных имён узла. | `{ oneOf: ["position", "inset"] }` |
| `order` | Сортирует группу с помощью `"alphabetical"` или порядка массива `oneOf` при `"exact"`. | `{ oneOf: ["display", "position"], order: "exact" }` |
| `splitItems` | Разделяет элементы группы пустыми строками, если включено разделение групп. | `{ type: "include", splitItems: true }` |

Поддерживаемые значения `type`: `use`, `extend`, `mixin`, `include`, `if`, `else`, `atrule`, `rule`, `decl`, `$variable`, `variable`, `media`, `supports` и `comment`. Привязка комментариев имеет приоритет перед порядком групп.

> Используйте `type: "decl"` вместе с `startsWith` или `oneOf`, если группа должна содержать только CSS-свойства. Без него критерий может также совпасть с именем или параметрами другого SCSS-узла.

## Режим безопасности

`grundyScssSorterSafety` принимает `"strict"` (по умолчанию) или `"loose"`. Старые имена `"conservative"` и `"structural"` остаются совместимыми алиасами для `"strict"` и `"loose"` соответственно, включая параметры CLI. Существующие конфигурации менять не требуется. Выбор пресета или пользовательских групп сам по себе не меняет режим. Strict применяет известные библиотеке ограничения, но не гарантирует семантическую эквивалентность произвольного SCSS.

```js
export default {
    plugins: ["prettier-grundy-scss-order"],
    grundyScssSorterSafety: "loose",
    grundyScssSorterGroupsOrder: ["$variable", "decl", "@include", "rule"]
};
```

`loose` применяет заданный порядок без границ выполнения и ограничений конфликтующих свойств. Можно перемещать переменные, вызовы, условия и модули, менять порядок shorthand/longhand. За результат выполнения SCSS отвечает пользователь. Оба режима сохраняют привязку комментариев, целые цепочки `if`/`else`, переводы строк после `//` и действие `prettier-ignore`. Настройки сортировки корня и разделения групп работают в обоих режимах. Неизвестные имена режимов отклоняются.

Описанная далее защита от конфликтов и перестановок через границы относится к режиму `strict`.

## Конфликтующие свойства

Исходный порядок потенциально конфликтующих деклараций важнее пресетов и пользовательских групп. Это сохраняет переопределения shorthand/longhand (например, `margin-top`, за которым следует `margin`), повторные fallback-декларации, алиасы и пересекающиеся логические/физические свойства. Независимые декларации продолжают сортироваться по настройкам.

Независимые физические смещения (`top`, `right`, `bottom`, `left`), толщина/стиль/цвет границ и border-image относительно радиусов, а также известные grid-свойства с непересекающимися longhand могут следовать заданному порядку. Перекрытия shorthand, логических/физических свойств и сброс `border-image` через `border` остаются защищены. Для неизвестных расширений семейств сохраняются консервативные проверки. Имена свойств с интерполяцией или экранированием и вложенные блоки Sass-свойств сохраняют положение относительно других деклараций.

## Границы выполнения

Присваивания Sass (`$value: ...`, в том числе с `!default`, `!global` и `theme.$value: ...`), `@include`, `@content`, управляющие директивы (`@if`/`@else`, `@for`, `@each`, `@while`, `@return`), диагностика (`@warn`, `@debug`, `@error`) и загрузка модулей (`@use`, `@forward`, `@import`) остаются на исходном месте. Другие конструкции не пересекают эти границы, даже если пресет или пользовательская группа задаёт иной порядок. CSS-переменные (`--value`) остаются сортируемыми декларациями.

Внешние блоки, содержащие такие операции, тоже остаются на месте, а каждая цепочка `@if`/`@else` сохраняется целиком на исходном месте. Их содержимое продолжает сортироваться рекурсивно между границами; `prettier-ignore` дополнительно защищает всё поддерево. Комментарии остаются привязаны к конструкциям, разделение групп пустыми строками сохраняется.

Это намеренно меняет прежнее форматирование, которое поднимало присваивания, условия или загрузку модулей. В частности, `@forward` и `@use` больше не перегруппировываются: их порядок может влиять на конфигурацию модулей и выдаваемый CSS. Неверное расположение загрузки модуля сохраняется для диагностики самим Sass.

В режиме `strict` пресеты, критерии групп, алфавитный/точный порядок и пустые строки работают внутри каждого сортируемого участка. Они не отменяют границы выполнения и конфликты свойств. Группы неподвижных конструкций влияют на разделение пустыми строками. Консервативные проверки могут запрещать и безвредные перестановки, особенно для внешних блоков и семейств `border`/`grid`. Явно выберите `loose`, когда приоритет должен иметь заданный вами порядок.

В `strict` декларация сохраняет исходную сторону относительно вложенного правила или CSS-блока, например `@media`, если блок может записать конфликтующее свойство. Учитываются shorthand-сбросы, логические свойства и динамические имена. Независимые декларации могут пересекать блок, его содержимое сортируется рекурсивно. Пересечение селекторов оценивается консервативно: даже непересекающиеся селекторы могут ограничить перенос конфликтующей декларации. `loose` разрешает заданные перестановки через такие блоки.

Сортировщик не выполняет Sass и не доказывает эквивалентность произвольных стилей. Побочные эффекты вызовов функций и зависимости каскада между двумя соседними правилами или CSS-блоками требуют отдельного анализа.

## Комментарии

Комментарии на отдельной строке перемещаются вместе со следующей конструкцией. Комментарии после конструкции на той же строке остаются с ней. Отдельные комментарии в конце блока остаются в конце. Пустая строка между группами добавляется перед ведущими комментариями.

`// prettier-ignore` и `/* prettier-ignore */` защищают следующую конструкцию и её содержимое от сортировки. Остальные конструкции сортируются отдельно до и после неё.
